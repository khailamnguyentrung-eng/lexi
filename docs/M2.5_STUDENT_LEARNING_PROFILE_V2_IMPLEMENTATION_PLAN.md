# M2.5 — StudentLearningProfile v2: Implementation Plan

_Created: 2026-06-29. Status: PLANNED — do not implement until approved._

---

## Overview

M2.5 is the capstone of Phase 2. It integrates all prior milestone outputs
(M2.1 SM-2, M2.2 Behavior Engine, M2.3 Adaptive Practice, M2.4 Learning Signals)
into a single unified learner model: `StudentLearningProfile v2`.

The profile already exists. M2.5 extends it with three new fields — one from each
missing output category — and adds the one schema migration Phase 2 was always planning.
No existing fields are removed or restructured. All new fields are nullable.

**What changes:** 3 new fields on the profile interface, 2 new lines in `Promise.all`,
1 two-pass assembly step, 1 pure function, 1 nullable DB column.

**What does not change:** Phase 1 fields, existing callers, UI components, behavior
engine, signal engine, difficulty calibration, mastery tracking, recommendation services.

---

## 1. Purpose of StudentLearningProfile v2

Phase 1 answered four questions:
- Where is the student now? (readiness, mastery, skill snapshot)
- What is improving? (learningTrend, improvingTopics)
- What needs attention? (activeWeaknesses)
- What should happen next? (recommendations, nextSession)

Phase 2 extensions answer three additional questions, completing the learner model:
- How is the student interacting? (behaviorProfile — M2.2, already on profile)
- What is the most important thing to surface right now? (topSignal — M2.4, NEW in M2.5)
- How much time is left? (examCountdown — from targetExamDate, NEW in M2.5)

M2.5 adds these two missing answers. The first (`topSignal`) closes the signal loop
from M2.4. The second (`examCountdown`) uses the one schema migration Phase 2 planned
from the start. A third field (`currentStreak`) moves the streak from a caller-side
parallel fetch into the profile itself, making the profile self-contained.

## 2. Profile Structure

The TypeScript interface remains **flat** — no sub-objects, no namespacing.
Re-grouping into `profile.knowledge.masterySummary` would break all existing callers
without delivering any technical benefit. The groupings below are conceptual, for
understanding where each field comes from and what it represents.

### Knowledge State — what the student knows and doesn't know

| Field | Type | Source |
|---|---|---|
| `masterySummary` | `MasterySummary` | Notebook + mastery tracking (Phase 1) |
| `improvingTopics` | `TopicMasteryProfile[]` | Mastery tracking (Phase 1) |
| `activeWeaknesses` | `ActiveWeakness[]` | Notebook + M2.1 SM-2 due counts (Phase 1) |

→ Already on profile. No changes in M2.5.

### Performance State — how the student is performing now

| Field | Type | Source |
|---|---|---|
| `readiness` | `ReadinessResult \| null` | Session analytics (Phase 1) |
| `skillSnapshot` | `SkillSnapshot[]` | Skill matrix (Phase 1) |
| `learningTrend` | `LearningTrend` | Derived from mastery distribution (Phase 1) |
| `topSignal` | `LearningSignal \| null` | **NEW** — M2.4 signal engine `computeLearningSignals()[0]` |

→ `topSignal` is the only new field in this group.

### Behavior State — how the student interacts with the system

| Field | Type | Source |
|---|---|---|
| `behaviorProfile` | `BehaviorProfile` | M2.2 behavior engine (already on profile) |
| `currentStreak` | `number` | **NEW** — `getLearningStreak()` (was fetched only in dashboard) |

→ `currentStreak` moves from caller-side to profile-level so that signal derivation
and countdown urgency can reference it without requiring an extra fetch from callers.

### Learning Preference — observed patterns about how the student prefers to work

Not new fields. These are named sub-dimensions of `behaviorProfile`, documented here
so downstream features know where to find them:

| Observation | Path |
|---|---|
| Preferred time of day | `behaviorProfile.preferredTimeOfDay` |
| Average session duration | `behaviorProfile.avgSessionDurationMin` |
| Mood context | `behaviorProfile.recentMoodContext` (contextual only — not a decision input) |

→ No new fields. Behavioral observations are already on `BehaviorProfile`.

### Problem Solving Style — inferred interaction patterns

Also sub-dimensions of `behaviorProfile`, not new fields:

| Pattern | Path |
|---|---|
| Pace across sessions | `behaviorProfile.paceProfile` (CONSISTENT / DECLINING / VARIABLE) |
| Response time pattern | `behaviorProfile.responseTimeSignal` (EXTENDED / MODERATE / BRIEF) |

→ No new fields. Documented here so future features (companion, hints) can reference them.

### Exam Countdown — time pressure context

| Field | Type | Source |
|---|---|---|
| `examCountdown` | `ExamCountdown \| null` | **NEW** — derived from `LearnerProfile.targetExamDate` |

→ `targetExamDate` is the one new DB column M2.5 adds to `LearnerProfile`.

### Navigation — curriculum position

| Field | Type | Source |
|---|---|---|
| `recommendations` | `PracticeRecommendation[]` | Recommendation service (Phase 1) |
| `nextSessionNumber` | `number \| null` | Curriculum service (Phase 1) |
| `nextSessionTitle` | `string \| null` | Curriculum service (Phase 1) |
| `nextSessionObjective` | `string \| null` | Curriculum service (Phase 1) |

→ Already on profile. No changes in M2.5.

## 3. Stored vs. Derived vs. Computed On Demand

### STORED in database

| What | Where | New? |
|---|---|---|
| `targetExamDate` (exam date set by student) | `LearnerProfile` | **YES — requires migration** |
| All other Phase 2 data (SM-2 fields, `timeSpentSec`, `startedAt`, mood, difficulty) | existing tables | No — already in schema |

`targetExamDate` is nullable (`DateTime?`). It is set by the student via profile settings
(a future route/form, not part of M2.5 itself). When null, `examCountdown` is null.

### DERIVED (computed from DB data, assembled as new values)

| What | How |
|---|---|
| `topSignal` | `computeLearningSignals(baseProfile, streak)[0] ?? null` |
| `examCountdown` | `computeExamCountdown(targetExamDate, now)` |
| `currentStreak` | `getLearningStreak(userId)` (async fetch, not derived from profile) |

### COMPUTED ON DEMAND (re-derived on every profile fetch, never cached)

All profile fields are computed on demand — this does not change in M2.5. The profile
is not stored or memoized between requests. Every call to `getStudentLearningProfile()`
re-runs the full fetch and derivation pipeline.

## 4. Integration: How M2.1–M2.4 Become One Learner Model

### What each milestone contributes to the profile

| Milestone | What it writes to the profile |
|---|---|
| **M2.1 SM-2** | `activeWeaknesses[n].dueCount` (SM-2 due count flows via notebook intelligence → `buildActiveWeaknesses`) |
| **M2.2 Behavior** | `behaviorProfile` (already integrated into profile since M2.2) |
| **M2.3 Adaptive** | Does NOT modify the profile — it modifies question SELECTION at practice time |
| **M2.4 Signals** | `topSignal` — integrated in M2.5 |
| **M2.5 Profile v2** | `currentStreak`, `topSignal`, `examCountdown` — this milestone |

### Integration point: `getStudentLearningProfile()`

M2.5 extends the existing `Promise.all` and the `buildLearningProfile()` call.
No new service files. No new repository files.

```
EXISTING PARALLEL FETCHES (6):
  getTopicNotebookSummaries(userId)
  getSkillMatrix(userId)
  getCurrentMission(userId)
  prisma.userSessionProgress.findFirst(...)   ← most recent completed session
  prisma.question.findMany(...)               ← for recommendation question counts
  getBehaviorProfile(userId)                  ← M2.2

NEW PARALLEL FETCHES (2, added in M2.5):
  getLearningStreak(userId)                   ← current streak count
  prisma.learnerProfile.findUnique(...)       ← select targetExamDate only

  Total: 8 parallel fetches in one Promise.all
```

```
SEQUENTIAL (after Promise.all):
  getSessionAnalytics(...)                    ← conditional, unchanged

PURE DERIVATION (unchanged):
  buildLearningProfile(ctx)                   ← now receives streak + targetExamDate in ctx
  → masterySummary, activeWeaknesses, learningTrend, improvingTopics ...
  → returns base profile (WITHOUT topSignal, currentStreak, examCountdown)

TWO-PASS EXTENSION (NEW in M2.5):
  computeLearningSignals(baseProfile, streak) ← M2.4 pure function; takes built profile
  computeExamCountdown(targetExamDate, now)   ← new pure function in M2.5

FINAL ASSEMBLY:
  return { ...baseProfile, topSignal: signals[0] ?? null, currentStreak: streak, examCountdown }
```

### Why two-pass?

`computeLearningSignals()` needs the completed `baseProfile` (it reads
`masterySummary`, `improvingTopics`, `activeWeaknesses`, `learningTrend`,
`behaviorProfile`). These fields are only available AFTER `buildLearningProfile()`.
A single pass would require duplicating the derivation logic. Two-pass avoids that.

## 5. Schema Impact

### New column

```prisma
model LearnerProfile {
  // ... existing fields ...

  targetExamDate  DateTime?   // student's target exam date; null until set
}
```

**Migration:** one nullable column on `LearnerProfile`. No existing row breaks.
When null: `examCountdown` returns null. When set: `computeExamCountdown()` runs.

### No other migrations

All other Phase 2 data (`easeFactor`, `reviewStage`, `nextReviewAt`, `timeSpentSec`,
`startedAt`, `completedAt`, `moodEntry`, `difficulty`) has been in the schema since
Phase 1 and was only missing write logic (now added by M2.1–M2.4).

### Backward compatibility

`LearnerProfile.targetExamDate` is optional. Rows without it receive `examCountdown: null`.
All Phase 1 and Phase 2 tests continue to pass — `targetExamDate` is simply `null` in
all existing data.

## 6. New Types and Functions

### New types (in `lib/analytics/studentLearningProfile.ts`)

```typescript
export interface ExamCountdown {
  targetExamDate: string;  // ISO date string, e.g. "2027-05-28"
  daysRemaining: number;   // positive = future; 0 = today; negative = past
  isUrgent: boolean;       // 0 < daysRemaining <= 30
}
```

### New pure function: `computeExamCountdown`

```typescript
// Pure — no DB access; takes now as parameter for testability
export function computeExamCountdown(
  targetExamDate: Date | null,
  now: Date
): ExamCountdown | null
```

- Returns `null` when `targetExamDate` is null
- `daysRemaining = Math.ceil((targetExamDate.getTime() − now.getTime()) / msPerDay)`
- `isUrgent = daysRemaining > 0 && daysRemaining <= 30`
- `targetExamDate` in output is `date.toISOString().split("T")[0]` (date only, no time)

### Updated `LearningProfileContext`

```typescript
export interface LearningProfileContext {
  // ... existing fields ...
  currentStreak: number;         // from getLearningStreak()
  targetExamDate: Date | null;   // from LearnerProfile
}
```

### Updated `StudentLearningProfile`

```typescript
export interface StudentLearningProfile {
  // ... all existing fields unchanged ...

  // Phase 2 additions — new in M2.5
  currentStreak: number;              // from getLearningStreak()
  topSignal: LearningSignal | null;   // highest-priority signal from M2.4
  examCountdown: ExamCountdown | null; // from LearnerProfile.targetExamDate
}
```

All three new fields are safe to access without null checks for `currentStreak`
(`number` — defaults to 0). `topSignal` and `examCountdown` are nullable and
callers must null-check before use.

## 8. Implementation Order

### Step 1 — Schema migration

Add `targetExamDate DateTime?` to `LearnerProfile` in `prisma/schema.prisma`.
Run `npx prisma migrate dev --name add_target_exam_date`.

### Step 2 — New types and `computeExamCountdown`

In `lib/analytics/studentLearningProfile.ts`:
1. Add `ExamCountdown` interface
2. Add `computeExamCountdown(targetExamDate, now)` pure function
3. Add `currentStreak: number` and `targetExamDate: Date | null` to `LearningProfileContext`
4. Add `currentStreak: number`, `topSignal: LearningSignal | null`,
   `examCountdown: ExamCountdown | null` to `StudentLearningProfile`

### Step 3 — Update `buildLearningProfile()`

Add to the return object:
```typescript
currentStreak: ctx.currentStreak,
examCountdown: computeExamCountdown(ctx.targetExamDate, new Date()),
// topSignal is NOT set here — requires the completed profile (two-pass)
```

`topSignal` is intentionally absent from `buildLearningProfile()` — it is set in
the two-pass step below.

### Step 4 — Update `getStudentLearningProfile()`

1. Add `getLearningStreak(userId)` to the existing `Promise.all`
2. Add `prisma.learnerProfile.findUnique({ where: { userId }, select: { targetExamDate: true } })`
   to the existing `Promise.all` (with `.catch(() => null)` — LearnerProfile may not exist)
3. Pass `currentStreak` and `targetExamDate` into `LearningProfileContext`
4. After `buildLearningProfile(ctx)` returns `baseProfile`, add two-pass:

```typescript
const baseProfile = buildLearningProfile(ctx);
const signals = computeLearningSignals(baseProfile, streak);
return { ...baseProfile, topSignal: signals[0] ?? null };
```

(`currentStreak` and `examCountdown` are already on `baseProfile` from Step 3.)

### Step 5 — Add import

In `lib/analytics/studentLearningProfile.ts`:
```typescript
import { computeLearningSignals } from "./learningSignalEngine";
import type { LearningSignal } from "./learningSignalEngine";
import { getLearningStreak } from "@/lib/services/streak";
```

### Step 6 — Barrel export

In `lib/analytics/index.ts`, add:
```typescript
export type { ExamCountdown } from "./studentLearningProfile";
```

### Step 7 — Test script

Create `scripts/test-profile-v2.mjs`. Add `"test:profile-v2"` to `package.json`.

### Step 8 — Verify


## 9. Testing Strategy

### New test file: `scripts/test-profile-v2.mjs`

Plain `.mjs`, no Prisma, no TypeScript compilation. Inlines `computeExamCountdown`
and a minimal mock of `buildLearningProfile`'s new fields.

### `computeExamCountdown` tests

| Test | Scenario |
|---|---|
| null input → null output | `targetExamDate = null` |
| Future date → positive daysRemaining | 45 days from now |
| Past date → negative daysRemaining | 10 days ago |
| Today → daysRemaining = 0 | Same day |
| 30 days remaining → isUrgent = true | Boundary |
| 29 days remaining → isUrgent = true | Below boundary |
| 31 days remaining → isUrgent = false | Above boundary |
| 0 days remaining → isUrgent = false (exam today, not "upcoming") | Boundary |
| Negative daysRemaining → isUrgent = false | Past exam |
| Output date format is ISO date string | "2027-05-28" format |

### Profile assembly tests

| Test | Scenario |
|---|---|
| Profile with `topSignal` present | signals produce non-null topSignal |
| Profile with no signals → `topSignal = null` | empty signal list |
| `currentStreak = 0` for new student | zero is valid |
| `currentStreak = 7` appears on profile | streak threaded through |
| `examCountdown = null` when `targetExamDate` absent | null LearnerProfile |

### What is NOT tested in this file

- Signal computation logic — tested in `test-learning-signals.mjs`
- Mastery/notebook logic — tested in existing Phase 1 scripts
- `getStudentLearningProfile()` (async, DB-dependent) — integration tested manually

Target: ~15 assertions.

## 10. Backward Compatibility

### Callers of `getStudentLearningProfile()`

| Caller | Impact |
|---|---|
| `app/(app)/dashboard/page.tsx` | Unchanged — new fields are additions, not removals. `learningProfile.topSignal` is accessible but not yet used in UI. |
| `app/(app)/practice/[sessionNumber]/results/page.tsx` | Unchanged — same as above. |
| `getLearningSignals(userId)` in M2.4 | Also calls `getStudentLearningProfile()`. After M2.5, `topSignal` will be present on the profile it fetches, but `getLearningSignals()` ignores it (it computes signals independently). No conflict. |

### Existing tests

No existing test script accesses `StudentLearningProfile` interface fields directly
(they test pure functions like `buildMasterySummary`, `deriveLearningTrend`). All
68 assertions in `test-learning-profile.mjs` continue to pass — they test the same
functions M2.5 does not modify.

### Dashboard `streak` variable

`dashboard/page.tsx` currently fetches `getLearningStreak(user.id)` in its own
`Promise.all` for display purposes. After M2.5, `learningProfile.currentStreak`
contains the same value. The dashboard does NOT need to change (it can keep its
own streak fetch for the header display). If a future cleanup removes the duplicate
fetch from the dashboard, that's a caller-side optimization, not M2.5 scope.

## 11. Risks and Mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Circular import: `studentLearningProfile.ts` → `learningSignalEngine.ts` → `studentLearningProfile.ts` | **Present** — must be checked | `learningSignalEngine.ts` imports `StudentLearningProfile` type only (not `getStudentLearningProfile`). TypeScript type-only imports don't create runtime circular deps. The import is `import type { StudentLearningProfile }` — no circular problem. |
| `getLearningStreak` is already called by `getLearningSignals(userId)`, which is called separately; M2.5 calls it again inside `getStudentLearningProfile` → double DB hit if both are called | Low | After M2.5, callers use `getStudentLearningProfile()` instead of `getLearningSignals()` for the top signal. The standalone `getLearningSignals()` is for callers that need ALL signals, not just the top one. Double fetch only occurs if both are called — which is unlikely once topSignal is on the profile. |
| `buildLearningProfile()` called from `test-learning-profile.mjs` tests — if we add required `currentStreak` to `LearningProfileContext`, existing test calls break | **Present** | Must update `test-learning-profile.mjs` to add `currentStreak: 0` and `targetExamDate: null` to test context objects. This is a small fix, not a rework. |
| `LearnerProfile` may not exist for a user (it's `profile?` on `User`) | Present | The new `prisma.learnerProfile.findUnique` fetch uses `.catch(() => null)` — missing profile returns null, `targetExamDate` defaults to null, `examCountdown` is null. |
