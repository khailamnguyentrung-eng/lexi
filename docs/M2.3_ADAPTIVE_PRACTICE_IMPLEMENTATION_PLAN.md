# M2.3 — Adaptive Practice Foundation: Implementation Plan

_Created: 2026-06-29. Status: PLANNED — do not implement until approved._

---

## Overview

M2.3 makes `getPracticeQuestions()` difficulty-aware. When a student has enough
practice history on a topic, the question selection skews toward the difficulty level
that matches their current accuracy — EASY to rebuild confidence when struggling,
HARD to maintain challenge when mastering.

No AI. No new DB columns. No event sourcing. No UI visual changes.
The student's session looks identical — they just receive better-matched questions.

---

## 1. Next Best Action Architecture

M2.3 is not a recommendation engine — it is a **question-selection modifier**.
The existing `computeRecommendations()` already decides what topic to practice.
M2.3 decides which questions to serve once that decision is made.

```
INPUT (per topic):
  mastery          ← MasteryState from masteryTracking.ts
  weakness         ← accuracy from sessionAnalytics / weaknessTopics
  retention        ← reviewStage from ErrorNotebookEntry (SM-2)
  behavior         ← responseTimeSignal, paceProfile from behaviorEngine.ts

                 ↓

DIFFICULTY TARGET ENGINE (pure)
  computeDifficultyTarget(recentAttempts)
  → DifficultyTarget: "EASY" | "MEDIUM" | "HARD" | null

                 ↓

QUESTION SELECTION (in getPracticeQuestions)
  Filter by topic → re-weight by DifficultyTarget → return calibrated set

                 ↓

OUTPUT:
  Question[]  (same shape as today — no interface change)
```

### How signals map to DifficultyTarget

| Signal | Rule | Target |
|---|---|---|
| Recent topic accuracy > 0.80 | Student is mastering this topic | HARD |
| Recent topic accuracy 0.50–0.80 | Student is in the working zone | MEDIUM |
| Recent topic accuracy < 0.50 | Student is struggling | EASY |
| < 5 recent attempts on this topic | Insufficient data | `null` → no re-weighting |

`BehaviorProfile` (M2.2) is available as **context** but does NOT determine difficulty
directly. `responseTimeSignal === "BRIEF"` may indicate a student is rushing, but brief
responses alone do not mean easier questions are needed — accuracy is the signal.
`BehaviorProfile` is reserved for M2.4 (signal engine) to surface as an observation.

**Mood context does NOT affect difficulty.** `recentMoodContext === "NEGATIVE"` does not
trigger EASY questions — that would be a psychological inference from a self-report
signal, violating the "behavior over self-report" principle and the plan constraint.

## 3. Existing Recommendation Compatibility

`computeRecommendations()` and `getAdaptiveRecommendations()` are **unchanged**.
They continue to decide WHAT to practice (topic selection, priority tier).
M2.3 only affects HOW questions are selected once a session is entered.

The existing flow:

```
Dashboard: computeRecommendations() → "Practice Conditionals"
Student clicks → practice/[sessionNumber] page
Page: getPracticeQuestions(session, user.id) → calibrated question set
```

M2.3 plugs into the second step only. The first step is untouched.

`PracticeRecommendation.suggestedAction` values (`REVIEW_NOTEBOOK`, `PRACTICE_TOPIC`,
`ADVANCE_SESSION`) are unchanged. No new recommendation type is added.

### Topic practice page

`practice/topic/[topic]/page.tsx` also calls `getPracticeQuestions`. This page currently
bypasses the curriculum session structure and is out of scope for M2.3 calibration — it
uses a different data flow. The `userId?` parameter is ignored when no calibration context
can be derived (returns standard question set). No change needed in that page.

## 5. Difficulty Selection Logic

### New file: `lib/analytics/difficultyCalibration.ts`

#### Types

```typescript
export type DifficultyTarget = "EASY" | "MEDIUM" | "HARD";

export interface AttemptForCalibration {
  isCorrect: boolean;
  difficulty: "EASY" | "MEDIUM" | "HARD";
}

export interface DifficultyWeights {
  EASY: number;   // fraction of questions to pull from EASY pool (sums to 1.0 with others)
  MEDIUM: number;
  HARD: number;
}
```

#### Pure function: `computeDifficultyTarget`

```typescript
export function computeDifficultyTarget(
  recentAttempts: AttemptForCalibration[],
  minSamples: number = 5
): DifficultyTarget | null
```

Returns `null` if `recentAttempts.length < minSamples` (insufficient data — caller
returns unmodified question set). Otherwise:

```
accuracy = correct / total

accuracy > 0.80  → HARD    (student ready for more challenge)
accuracy ≥ 0.50  → MEDIUM  (working zone — maintain current level)
accuracy < 0.50  → EASY    (struggling — reduce friction)
```

Uses the **last N attempts** for the topic, already filtered by the caller. The function
does not fetch from DB — it receives pre-filtered attempts from the repository call inside
`getPracticeQuestions()`.

#### Pure function: `computeSelectionWeights`

```typescript
export function computeSelectionWeights(target: DifficultyTarget): DifficultyWeights
```

| Target | EASY weight | MEDIUM weight | HARD weight |
|---|---|---|---|
| EASY | 0.70 | 0.25 | 0.05 |
| MEDIUM | 0.20 | 0.55 | 0.25 |
| HARD | 0.05 | 0.25 | 0.70 |

These weights are **selection proportions**, not strict filters. If a pool is empty for
a given difficulty (e.g. no HARD questions exist for a topic), weight is redistributed
to the next preferred level: HARD→MEDIUM, EASY→MEDIUM.

#### Selection algorithm (in `getPracticeQuestions`)

When `userId` is provided and calibration applies:

1. Group available questions by difficulty: `{ EASY: Q[], MEDIUM: Q[], HARD: Q[] }`
2. Fetch the student's last 20 `QuestionAttempt` records for this session's topics
   (join with `question.difficulty`, `question.topic`)
3. Group attempts per canonical topic → compute `DifficultyTarget` per topic
4. For sessions with mixed topics, compute a **session-level target** by taking the
   modal topic target (most common target across topics; ties broken by MEDIUM)
5. Compute `DifficultyWeights` from the session-level target
6. Select questions by weighted sampling from each difficulty pool
7. If total available questions ≤ session question count: return all as-is (no selection
   needed — no calibration overhead)

#### Bypass rules

| Condition | Behavior |
|---|---|
| `session.sessionType === "MOCK_EXAM"` | Return full question set unchanged |
| `session.sessionType === "CHECKPOINT"` | Return unweighted random selection |
| `userId` not provided | Return current behavior (fallback chain unchanged) |
| `recentAttempts.length < 5` per topic | Return questions for that topic unweighted |
| Available questions ≤ required count | Return all questions (no selection possible) |

## 6. Implementation Order

### Step 1 — Create `lib/analytics/difficultyCalibration.ts`

1. Define `DifficultyTarget`, `AttemptForCalibration`, `DifficultyWeights` types
2. Implement `computeDifficultyTarget(attempts, minSamples?)` pure function
3. Implement `computeSelectionWeights(target)` pure function
4. Implement `applyDifficultyWeighting(questions, weights)` pure function
   — takes `Question[]` grouped by difficulty, applies weights, returns selected `Question[]`

### Step 2 — Extend `lib/services/curriculum.ts`

1. Add `userId?: string` to `getPracticeQuestions` signature
2. When `userId` is provided:
   a. Determine if calibration applies (not MOCK_EXAM, not CHECKPOINT)
   b. Fetch recent attempts: `prisma.questionAttempt.findMany` with question difficulty join
   c. Compute `DifficultyTarget` per topic via `computeDifficultyTarget()`
   d. Derive session-level target (modal)
   e. Apply `applyDifficultyWeighting()` to select from available questions
3. All new logic inside a try/catch — failure falls back to existing behavior silently

### Step 3 — Update `app/(app)/practice/[sessionNumber]/page.tsx`

One line change only: pass `user.id` to `getPracticeQuestions`:

```typescript
// Before:
const questions = await getPracticeQuestions(session);

// After:
const questions = await getPracticeQuestions(session, user.id);
```

`user` is already fetched on line 8. This is the only page-level change.
`PracticeQuiz` receives the same prop shape — no component changes.

### Step 4 — Export from barrel

Add to `lib/analytics/index.ts`:
```typescript

export { computeDifficultyTarget, computeSelectionWeights } from "./difficultyCalibration";
```

## 8. Backward Compatibility

### Existing callers of `getPracticeQuestions`

| Caller | Current call | After M2.3 |
|---|---|---|
| `practice/[sessionNumber]/page.tsx` | `getPracticeQuestions(session)` | `getPracticeQuestions(session, user.id)` — one-line change |
| `practice/topic/[topic]/page.tsx` | Different flow — does not call this function directly | Unchanged |

`userId?` is optional — any caller not updated continues working without calibration.
TypeScript enforces this via the optional parameter: no existing call breaks.

### Phase 1 analytics layer

No Phase 1 files are modified. `difficultyCalibration.ts` is a new file. `curriculum.ts`
is a service file (not analytics), and the change is additive (one optional parameter).

### M2.1 (SM-2)

Unchanged. `applySM2ForSession` runs at session completion — independent of question
selection. SM-2 continues to update `reviewStage` and `easeFactor` based on session
accuracy regardless of which difficulty questions were served.

### M2.2 (BehaviorEngine)

`BehaviorProfile` is available in `StudentLearningProfile` but is **not consumed by
M2.3** at the question-selection level. `responseTimeSignal` and `paceProfile` may
inform M2.4 signals but do not gate or adjust `DifficultyTarget`.

### Session types that must not adapt

| Session type | Reason for bypass |
|---|---|
| `MOCK_EXAM` | Full question set required — the real exam does not adapt |
| `CHECKPOINT` | Must sample evenly across topics — calibration would skew coverage |

These bypasses are enforced inside `getPracticeQuestions()`, not at the call site.

## 9. Risks and Mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Too few questions per difficulty tier | Medium | Fallback: redistribute weight to MEDIUM if a pool is empty |
| `QuestionAttempt.curriculumSessionId` null on old records | Medium | Filter to non-null only; insufficient data → `null` target → no calibration |
| Calibration adds latency to page load | Low | Single extra DB query (last 20 attempts); negligible vs. existing page queries |
| All seed questions currently EASY or MEDIUM | Present | Calibration still works with available pools; HARD weight falls through to MEDIUM |
| `question.difficulty` field value distribution is unknown | Medium | `computeDifficultyTarget` returns `null` when data is thin — safe fallback |
