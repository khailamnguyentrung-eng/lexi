# M2.2 — Learning Behavior Engine: Implementation Plan

_Created: 2026-06-28. Status: PLANNED — do not implement until approved._

---

## Overview

M2.2 introduces `lib/analytics/behaviorEngine.ts` — a pure analytics module that
answers **"How does this learner learn?"** from observed behavioral signals in the
existing schema. No schema migration, no AI scoring, no event sourcing.

The output is a `BehaviorProfile` that is eventually surfaced through
`StudentLearningProfile` and used by M2.4 (Adaptive Practice) to personalize session
recommendations.

---

## 1. Available Learning Signals

### What exists in the schema today

| Signal | Source field | Quality |
|---|---|---|
| Session timing | `UserSessionProgress.startedAt`, `completedAt` | nullable — not all sessions record both |
| Per-question time | `QuestionAttempt.timeSpentSec` | nullable `Int?` — only populated when client sends it |
| Per-question result | `QuestionAttempt.isCorrect` | always present |
| Session link | `QuestionAttempt.curriculumSessionId` | nullable — some attempts not linked to a session |
| Mood self-report | `MoodEntry.mood` (GREAT/GOOD/OKAY/TIRED/STRESSED) | voluntary — may be sparse |
| Session status | `UserSessionProgress.status` (COMPLETED etc.) | always present |

### What is NOT available (and must NOT be assumed)

| Signal | Why unavailable |
|---|---|
| Hint usage | No hint system exists in schema — `QuestionAttempt` has no hint column |
| Per-question retries | No per-question attempt count column — only one row per `(userId, questionId, sessionId)` |
| Preferred difficulty | No difficulty column on `Question` — added in M2.3 |
| Attempt timestamp accuracy | `attemptedAt` exists but granularity depends on client behavior |

### Derivable behavioral signals (from available data)

| Behavior Signal | Derivation |
|---|---|
| **Preferred time of day** | `startedAt` hour → MORNING/AFTERNOON/EVENING bucket |
| **Pace profile** | First-third accuracy vs last-third accuracy within sessions |
| **Session duration** | `completedAt − startedAt` in minutes (when both non-null) |
| **Effort signal** | Average `timeSpentSec` across non-null attempts |
| **Mood trend** | Distribution of last N `MoodEntry.mood` values |
| **Consistency** | `sessionCount` and `confidenceTier` — indirect proxy |

### Signals requested but unavailable

`retry behavior`, `persistence`, and `hint dependency` are listed in the Phase 2 product
spec but have no data source in the current schema. These fields are **omitted** from
`BehaviorProfile` until the schema provides the underlying data. They must not be guessed
or approximated from unrelated fields.

## 2. BehaviorProfile Design

### Type definitions

```typescript
export type SessionTimeOfDay = "MORNING" | "AFTERNOON" | "EVENING";
// MORNING:   06:00–11:59
// AFTERNOON: 12:00–17:59
// EVENING:   18:00–23:59
// Night (00:00–05:59) → mapped to EVENING (edge case, same behavior)

export type PaceProfile = "CONSISTENT" | "DECLINING" | "VARIABLE";
// Method: split attempts per session into first-third and last-third by attemptedAt.
// Compare accuracy between the two thirds.
// CONSISTENT: |firstAccuracy − lastAccuracy| < 0.15 across the majority of sessions
// DECLINING:  lastAccuracy < firstAccuracy by ≥ 0.15 in majority of sessions
// VARIABLE:   neither pattern holds consistently

export type EffortSignal = "HIGH" | "MODERATE" | "LOW";
// Derived from median timeSpentSec across all non-null attempt records.
// HIGH:     median ≥ 30s
// MODERATE: 10s ≤ median < 30s
// LOW:      median < 10s OR fewer than 5 non-null records (insufficient data)

export type MoodTrend = "POSITIVE" | "NEUTRAL" | "NEGATIVE";
// Derived from last 7 MoodEntry records (ordered by createdAt DESC).
// POSITIVE: majority (≥ 4) are GREAT or GOOD
// NEGATIVE: majority (≥ 4) are TIRED or STRESSED
// NEUTRAL:  otherwise (mixed or OKAY-dominated)

export interface BehaviorProfile {
  preferredTimeOfDay: SessionTimeOfDay | null;  // null: < 5 sessions with startedAt
  paceProfile: PaceProfile | null;              // null: < 3 sessions with attempt data
  avgSessionDurationMin: number | null;         // null: no startedAt/completedAt pairs
  effortSignal: EffortSignal | null;            // null: < 5 non-null timeSpentSec records
  recentMoodTrend: MoodTrend | null;            // null: < 5 mood entries
  sessionCount: number;                         // total COMPLETED sessions analyzed
  confidenceTier: ConfidenceTier;               // OBSERVED | EMERGING | CONFIRMED
}
```

### Field semantics

| Field | Meaning | Used by |
|---|---|---|
| `preferredTimeOfDay` | When this student typically studies | M2.4: scheduling hints |
| `paceProfile` | Whether performance holds or degrades within sessions | M2.4: session length recommendations |
| `avgSessionDurationMin` | How long sessions actually last | M2.4: pacing |
| `effortSignal` | How much time student spends per question | M2.3: surface as engagement signal |
| `recentMoodTrend` | Emotional state in recent days | M2.4: difficulty adjustment |
| `sessionCount` | Total sessions analyzed | confidence tier computation |
| `confidenceTier` | Data reliability of the profile | UI: suppress fields when OBSERVED |

### Confidence tier thresholds

| `sessionCount` | `confidenceTier` |
|---|---|
| 0–4 | OBSERVED |
| 5–9 | EMERGING |
| 10+ | CONFIRMED |

When `confidenceTier` is `OBSERVED`, most fields will be `null`. The profile is always
returned (never thrown) — consumers render an empty-state gracefully.

## 3. Behavior Engine Architecture

```
Raw Data (DB)
  UserSessionProgress (COMPLETED, with startedAt/completedAt)
  QuestionAttempt (isCorrect, timeSpentSec, attemptedAt, curriculumSessionId)
  MoodEntry (mood, createdAt)
        ↓
Repository Layer  [getBehaviorProfile — has Prisma access]
  Fetches data, shapes into SessionDataPoint[] + MoodDataPoint[]
        ↓
Pure Engine  [computeBehaviorProfile — no Prisma, no side effects]
  Derives all signals from pre-fetched arrays
  Returns BehaviorProfile
        ↓
BehaviorProfile
        ↓
StudentLearningProfile  [extended in M2.2 to include behaviorProfile field]
        ↓
UI  [reads behaviorProfile, no logic]
```

### File

**New file:** `lib/analytics/behaviorEngine.ts`

All exported types and functions live here. Nothing in Phase 1 is modified.

### Exports

```typescript
// Types (exported)
export type { SessionTimeOfDay, PaceProfile, EffortSignal, MoodTrend, BehaviorProfile }

// Pure engine (no Prisma)
export function computeBehaviorProfile(
  sessions: SessionDataPoint[],
  moodEntries: MoodDataPoint[]
): BehaviorProfile

// Repository function (has Prisma)
export async function getBehaviorProfile(userId: string): Promise<BehaviorProfile>
```

### Internal input types (not exported — used only by pure engine)

```typescript
interface SessionDataPoint {
  startedAt: Date | null;
  completedAt: Date | null;
  attempts: {
    isCorrect: boolean;
    timeSpentSec: number | null;
    attemptedAt: Date;
  }[];
}

interface MoodDataPoint {
  mood: "GREAT" | "GOOD" | "OKAY" | "TIRED" | "STRESSED";
  createdAt: Date;
}
```

### Pure engine function internals

`computeBehaviorProfile(sessions, moodEntries)` calls five private helpers:

| Helper | Input | Output |
|---|---|---|
| `deriveTimeOfDay(sessions)` | `SessionDataPoint[]` | `SessionTimeOfDay \| null` |
| `derivePaceProfile(sessions)` | `SessionDataPoint[]` | `PaceProfile \| null` |
| `deriveAvgDuration(sessions)` | `SessionDataPoint[]` | `number \| null` |
| `deriveEffortSignal(sessions)` | `SessionDataPoint[]` | `EffortSignal \| null` |
| `deriveMoodTrend(moodEntries)` | `MoodDataPoint[]` | `MoodTrend \| null` |

Each helper returns `null` when data is insufficient rather than guessing.

### Repository fetch plan

`getBehaviorProfile(userId)` fetches in one `Promise.all`:

```
1. prisma.userSessionProgress.findMany
     where: { userId, status: "COMPLETED" }
     select: { id, startedAt, completedAt }
     orderBy: { completedAt: "desc" }
     take: 30  // last 30 sessions — sufficient for all signal derivations

2. prisma.questionAttempt.findMany
     where: { userId, curriculumSessionId: { in: sessionIds } }
     select: { isCorrect, timeSpentSec, attemptedAt, curriculumSessionId }

3. prisma.moodEntry.findMany
     where: { userId }
     orderBy: { createdAt: "desc" }
     take: 14  // last 14 entries; 7 used for trend, extra buffer
```

Then groups attempts by `curriculumSessionId`, builds `SessionDataPoint[]`, passes to
`computeBehaviorProfile()`.

## 5. Schema Impact

### Assessment

| Need | Schema field | Status |
|---|---|---|
| Session start time | `UserSessionProgress.startedAt` | Exists (`DateTime?`) |
| Session end time | `UserSessionProgress.completedAt` | Exists (`DateTime?`) |
| Session status | `UserSessionProgress.status` | Exists |
| Per-question time | `QuestionAttempt.timeSpentSec` | Exists (`Int?`) |
| Per-question result | `QuestionAttempt.isCorrect` | Exists |
| Attempt timestamp | `QuestionAttempt.attemptedAt` | Exists |
| Session link on attempt | `QuestionAttempt.curriculumSessionId` | Exists (`String?`) |
| Mood data | `MoodEntry.mood`, `MoodEntry.createdAt` | Exists |

### Conclusion

**No schema migration required for M2.2.**

All fields needed to compute `BehaviorProfile` already exist. The nullable nature of
`startedAt`, `completedAt`, and `timeSpentSec` is handled by the engine returning `null`
for signals where data is insufficient — not by schema changes.

### Future schema additions (NOT in M2.2)

| Signal | Future column needed |
|---|---|
| Hint usage | `QuestionAttempt.hintUsed Boolean` |
| Retry count | `QuestionAttempt.retryCount Int` or separate `QuestionRetry` table |

These belong to a future phase when the hint system is built. They are noted here so the
schema design for M2.3+ can account for them, but must not be added in M2.2.

## 6. Implementation Order

### Step 1 — Create `lib/analytics/behaviorEngine.ts`

1. Define `SessionTimeOfDay`, `PaceProfile`, `EffortSignal`, `MoodTrend`, `BehaviorProfile` types
2. Define internal `SessionDataPoint`, `MoodDataPoint` types (not exported)
3. Implement five private derivation helpers (each returns `T | null`):
   - `deriveTimeOfDay(sessions)`
   - `derivePaceProfile(sessions)`
   - `deriveAvgDuration(sessions)`
   - `deriveEffortSignal(sessions)`
   - `deriveMoodTrend(moodEntries)`
4. Implement `computeBehaviorProfile(sessions, moodEntries)` — calls all five helpers,
   computes `sessionCount` and `confidenceTier`, returns `BehaviorProfile`
5. Implement `getBehaviorProfile(userId)` — three-query Promise.all, data assembly,
   delegates to `computeBehaviorProfile()`

### Step 2 — Extend `StudentLearningProfile` (minimal Phase 1 touch)

1. Add `behaviorProfile: BehaviorProfile` to `StudentLearningProfile` interface
2. Add `behaviorProfile: BehaviorProfile` to `LearningProfileContext` interface
3. In `getStudentLearningProfile()`: add `getBehaviorProfile(userId)` to the existing `Promise.all`
4. Pass `behaviorProfile` through in `buildLearningProfile()` → return shape

### Step 3 — Write test script `scripts/test-behavior-engine.mjs`

(See §7 for coverage plan.)

### Null safety contract

`getBehaviorProfile()` **never throws**. If the DB queries return zero rows, the function
returns a valid `BehaviorProfile` with all nullable fields set to `null` and
`confidenceTier: "OBSERVED"`. Consumers are always guaranteed a non-null
`BehaviorProfile` object — they check field nullability, not profile nullability.

This mirrors M2.1's try/catch pattern: the behavior engine failing must never break the
`StudentLearningProfile` load. In `getStudentLearningProfile()`, wrap the
`getBehaviorProfile()` call in try/catch and fall back to an all-null default profile if
it throws.

## 9. Risks and Mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| `timeSpentSec` sparsely populated | High | `EffortSignal` returns null for < 5 records; not a failure |
| `startedAt`/`completedAt` often null | Medium | `avgSessionDurationMin` returns null gracefully |
| `curriculumSessionId` null on some attempts | Medium | Filter to non-null before join; sessions without attempts produce no pace data |
| `StudentLearningProfile` callers break | Low | New field is additive; existing destructuring is unaffected in TypeScript |
| `behaviorEngine.ts` circular import | Low | Does not import from `studentLearningProfile.ts`; only `studentLearningProfile.ts` imports from it |
