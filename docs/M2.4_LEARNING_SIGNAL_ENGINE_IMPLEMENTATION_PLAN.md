# M2.4 — Learning Signal Engine: Implementation Plan

_Created: 2026-06-29. Status: PLANNED — do not implement until approved._

---

## Overview

M2.4 converts the existing `StudentLearningProfile` state into a set of named,
structured **learning signals** — deterministic observations that the system can
surface to the student or pass downstream to M2.5 and future companions.

A learning signal is not a recommendation ("practice conditionals") and not a
narrative sentence ("you improved this week"). It is a typed, machine-readable
fact derived from observed data, together with enough metadata to decide whether
and how to show it.

No AI. No new DB columns. No new DB queries beyond what `StudentLearningProfile`
and `getLearningStreak()` already provide.

---

## 1. Learning Signal Architecture

```
EXISTING DATA LAYER (no new queries in M2.4)
  StudentLearningProfile (includes BehaviorProfile from M2.2)
  getLearningStreak()    (existing streak service)

              ↓  pre-fetched by service function

PURE ENGINE   lib/analytics/learningSignals.ts
  computeLearningSignals(profile, currentStreak)
              → LearningSignal[]    sorted by severity DESC

              ↓  consumed by

OUTPUTS
  getLearningSignals(userId)     — standalone service function
  StudentLearningProfile.signals — added in M2.5 (not M2.4)
  Future: companion UI, coach prompts, M2.5 topSignal
```

### What feeds the engine

| Input | Source | Available now |
|---|---|---|
| `masterySummary.masteredTopics` | `StudentLearningProfile` | ✓ |
| `improvingTopics` (IMPROVING/STABLE state list) | `StudentLearningProfile` | ✓ |
| `activeWeaknesses` (RECURRING/NEEDS_REVIEW topics) | `StudentLearningProfile` | ✓ |
| `learningTrend` (PROGRESSING/STABLE/NEEDS_ATTENTION/INSUFFICIENT_DATA) | `StudentLearningProfile` | ✓ |

| `behaviorProfile.sessionCount` | `StudentLearningProfile.behaviorProfile` (M2.2) | ✓ |

no Prisma access.

## 2. Signal Types

### Complete signal type list

| SignalType | Trigger condition | Severity | Confidence basis |
|---|---|---|---|
| `FIRST_MASTERY` | `masterySummary.masteredTopics.length === 1` | HIGH | CONFIRMED (mastery is a strong threshold) |
| `TOPIC_MASTERED` | any topic in `masteredTopics` | MEDIUM | CONFIRMED |
| `TOPIC_IMPROVING` | any topic in `improvingTopics` where `masteryState === "IMPROVING"` | MEDIUM | derived from `totalOccurrences` |
| `RECURRING_WEAKNESS` | any `activeWeakness` where `signal === "RECURRING"` AND `totalOccurrences >= 3` | HIGH | derived from `totalOccurrences` |
| `RETENTION_RISK` | any `activeWeakness` where `dueCount > 0` AND `signal !== "RECURRING"` | MEDIUM | LOW (single due item) to HIGH (multiple overdue) |
| `LEARNING_MOMENTUM` | `learningTrend === "PROGRESSING"` | MEDIUM | derived from mastery counts |
| `PACE_OBSERVATION` | `behaviorProfile.paceProfile === "DECLINING"` AND `sessionCount >= 3` | LOW | LOW |
| `STREAK_MILESTONE` | `currentStreak` ∈ {3, 7, 14, 30} | MEDIUM | CONFIRMED (exact count) |

### Signal scope

| SignalType | Scope | `topic` field |
|---|---|---|
| `FIRST_MASTERY` | Global | `null` |
| `TOPIC_MASTERED` | Per topic | canonical topic string |
| `TOPIC_IMPROVING` | Per topic | canonical topic string |
| `RECURRING_WEAKNESS` | Per topic | canonical topic string |
| `RETENTION_RISK` | Per topic | canonical topic string |
| `LEARNING_MOMENTUM` | Global | `null` |
| `PACE_OBSERVATION` | Global | `null` |
| `STREAK_MILESTONE` | Global | `null` |

### Signals NOT included

| Requested signal | Why deferred |
|---|---|
| "declining" (topic regression) | Requires historical profile snapshots to detect transition from IMPROVED → RECURRING. Current schema has no stored previous state. Deferring until M2.5 or later adds a comparison point. |
| `EFFORT_RECOGNITION` | Required `behavior.effortSignal === "HIGH"` — this field was renamed to `responseTimeSignal` in M2.2 to avoid psychological inference. Response-time signal does not reliably proxy effort. Deferred. |
| `NOTEBOOK_CLEARED` | Requires "3+ topics newly MASTERED vs. last profile" — needs stored previous snapshot. Not available without schema change. Deferred. |

## 3. LearningSignal Shape

```typescript
export type SignalType =
  | "FIRST_MASTERY"
  | "TOPIC_MASTERED"
  | "TOPIC_IMPROVING"
  | "RECURRING_WEAKNESS"
  | "RETENTION_RISK"
  | "LEARNING_MOMENTUM"
  | "PACE_OBSERVATION"
  | "STREAK_MILESTONE";

// How serious or urgent is this signal?
// CRITICAL: would need intervention — reserved for future use (e.g. exam < 7 days + NEEDS_ATTENTION)
// HIGH:     notable, actionable (mastery achieved, strong recurring pattern)
// MEDIUM:   encouraging or moderately actionable (improving, streak, retention due)
// LOW:      soft observation, informational (pace pattern, weak signal)
export type SignalSeverity = "CRITICAL" | "HIGH" | "MEDIUM" | "LOW";

// How reliable is the data behind this signal?
// Mirrors the ConfidenceTier concept from Phase 1 — same 3-tier scheme, different name.
export type SignalConfidence = "HIGH" | "MEDIUM" | "LOW";

// Structured evidence — the raw facts that produced this signal.
// All fields optional; only the relevant subset is populated per signal type.
export interface SignalEvidence {
  occurrenceCount?: number;    // times topic appeared in notebook (RECURRING_WEAKNESS)
  dueCount?: number;           // SM-2 entries currently overdue (RETENTION_RISK)
  reviewStage?: number;        // SM-2 stage at time of signal (RETENTION_RISK)
  masteredCount?: number;      // total mastered topics (FIRST_MASTERY, TOPIC_MASTERED)
  improvingCount?: number;     // topics currently IMPROVING (TOPIC_IMPROVING)
  currentStreak?: number;      // consecutive active days (STREAK_MILESTONE)
  sessionCount?: number;       // sessions analyzed for behavior (PACE_OBSERVATION)
}

export interface LearningSignal {
  type: SignalType;
  severity: SignalSeverity;
  topic: string | null;        // canonical topic key, or null for global signals
  topicLabel: string | null;   // display label for the topic, or null
  evidence: SignalEvidence;
  confidence: SignalConfidence;
  generatedAt: string;         // ISO timestamp when computeLearningSignals() ran
  suppressionKey: string;      // unique key for deduplication across sessions
  // e.g. "STREAK_MILESTONE_7", "RECURRING_WEAKNESS_conditionals"
}
```

### suppressionKey format

| SignalType | Format | Example |
|---|---|---|
| `FIRST_MASTERY` | `"FIRST_MASTERY"` | `"FIRST_MASTERY"` |
| `TOPIC_MASTERED` | `"TOPIC_MASTERED_{topic}"` | `"TOPIC_MASTERED_conditionals"` |
| `TOPIC_IMPROVING` | `"TOPIC_IMPROVING_{topic}"` | `"TOPIC_IMPROVING_present_perfect"` |
| `RECURRING_WEAKNESS` | `"RECURRING_WEAKNESS_{topic}"` | `"RECURRING_WEAKNESS_articles"` |
| `RETENTION_RISK` | `"RETENTION_RISK_{topic}"` | `"RETENTION_RISK_passive_voice"` |
| `LEARNING_MOMENTUM` | `"LEARNING_MOMENTUM"` | `"LEARNING_MOMENTUM"` |
| `PACE_OBSERVATION` | `"PACE_OBSERVATION"` | `"PACE_OBSERVATION"` |
| `STREAK_MILESTONE` | `"STREAK_MILESTONE_{n}"` | `"STREAK_MILESTONE_7"` |

## 4. Pure Engine Functions

### New file: `lib/analytics/learningSignals.ts`

All logic is in pure functions. No Prisma inside the engine.

```typescript
// Primary export — no DB access
export function computeLearningSignals(
  profile: StudentLearningProfile,
  currentStreak: number
): LearningSignal[]
```

Returns signals sorted by `severity` DESC (`CRITICAL` → `HIGH` → `MEDIUM` → `LOW`).
Within the same severity, ordering is: topic-specific signals before global signals.
Empty array is valid — no signals is a correct output.

### Internal derivation functions (private, non-exported)

| Function | Derives |
|---|---|
| `deriveFirstMasterySignal(profile)` | `FIRST_MASTERY` if exactly 1 mastered topic |
| `deriveMasteredSignals(profile)` | `TOPIC_MASTERED` per mastered topic (except when FIRST_MASTERY fires — avoid duplication) |
| `deriveImprovingSignals(profile)` | `TOPIC_IMPROVING` per improving topic |
| `deriveRecurringWeaknessSignals(profile)` | `RECURRING_WEAKNESS` per active weakness with RECURRING signal and ≥ 3 occurrences |
| `deriveRetentionRiskSignals(profile)` | `RETENTION_RISK` per active weakness where dueCount > 0 AND signal is not RECURRING (RECURRING already captured above) |
| `deriveLearningMomentumSignal(profile)` | `LEARNING_MOMENTUM` if learningTrend === "PROGRESSING" |
| `derivePaceObservationSignal(profile)` | `PACE_OBSERVATION` if behaviorProfile.paceProfile === "DECLINING" AND sessionCount >= 3 |
| `deriveStreakMilestoneSignal(streak)` | `STREAK_MILESTONE` if streak ∈ {3, 7, 14, 30} |

### Confidence derivation rules

| SignalType | Confidence | Rule |
|---|---|---|
| `FIRST_MASTERY`, `TOPIC_MASTERED` | HIGH | Mastery threshold is already strict — signal is reliable |
| `TOPIC_IMPROVING` | HIGH if totalOccurrences ≥ 5; MEDIUM if 3–4; LOW if < 3 | More practice history = more confidence |
| `RECURRING_WEAKNESS` | HIGH if totalOccurrences ≥ 5; MEDIUM if 3–4 | Same as above |
| `RETENTION_RISK` | HIGH if dueCount ≥ 3; MEDIUM if dueCount = 2; LOW if dueCount = 1 | More overdue items = more urgent signal |
| `LEARNING_MOMENTUM` | HIGH if CONFIRMED behavior tier; MEDIUM if EMERGING; LOW if OBSERVED | Proxied from `behaviorProfile.confidenceTier` if available, else MEDIUM |
| `PACE_OBSERVATION` | LOW always | Behavioral observation — not a performance fact |
| `STREAK_MILESTONE` | HIGH always | Streak is a precise count |

### Signal cap

`computeLearningSignals()` returns at most **5 signals** per call. When more than
5 conditions are met simultaneously (e.g. 3 mastered topics + 2 weaknesses + a streak),
the highest-severity signals are returned first. This cap prevents signal flooding
on a student who has accumulated a lot of history.

## 5. Service Boundary

```
lib/analytics/learningSignals.ts
  computeLearningSignals(profile, streak)   ← pure, exported
  getLearningSignals(userId)                ← repository wrapper, exported

lib/services/streak.ts
  getLearningStreak(userId)                 ← already exists, used by getLearningSignals

lib/analytics/studentLearningProfile.ts    ← NOT modified in M2.4 (M2.5 responsibility)

lib/analytics/index.ts                     ← add learningSignals exports
```

### `getLearningSignals(userId)` implementation sketch

```typescript
export async function getLearningSignals(userId: string): Promise<LearningSignal[]> {
  const [profile, streak] = await Promise.all([
    getStudentLearningProfile(userId),
    getLearningStreak(userId),
  ]);
  return computeLearningSignals(profile, streak);
}
```

Both fetches are independent and run in parallel. `getStudentLearningProfile` already
includes `behaviorProfile` from M2.2. No additional DB queries needed beyond these two.

### Conclusion

**No schema migration required for M2.4.**

All signal derivations operate on data already assembled by `getStudentLearningProfile()`
and `getLearningStreak()`. No new Prisma models, no new columns, no migrations.

### Deferred signals that WOULD need schema

| Signal | Missing data |
|---|---|
| "declining" (topic regression) | Previous `StudentLearningProfile` snapshot — would need a stored state or `ProfileSnapshot` table |
| `NOTEBOOK_CLEARED` | Previous mastery count — same issue |
| `EFFORT_RECOGNITION` | Reliable effort proxy — `timeSpentSec` is sparse and not a reliable effort signal |

These are explicitly deferred. If a `ProfileSnapshot` table is added in a future phase,
these signals can be added to `computeLearningSignals()` without changing its signature.

## 8. Testing Strategy

### Test file: `scripts/test-learning-signals.mjs`

Plain `.mjs`, no Prisma, inlines all pure functions and the private helpers.
Uses the same `assert()` pattern as prior test scripts.

### Profile builder helpers

The test file needs a `makeProfile(overrides)` helper that builds a minimal valid
`StudentLearningProfile`-shaped object with sensible defaults, then merges overrides.
Similarly a `makeBehaviorProfile(overrides)` and `makeWeakness(overrides)` helper.
This avoids large object literals in every test.

### Test groups

| Group | Scenarios | Count |
|---|---|---|
| `FIRST_MASTERY` | exactly 1 mastered topic → HIGH severity; 0 mastered → no signal; 2+ mastered → TOPIC_MASTERED not FIRST_MASTERY | 3 |
| `TOPIC_MASTERED` | 1 mastered (should fire alongside FIRST_MASTERY check); 2 mastered → 2 signals; 0 mastered → none | 3 |
| `TOPIC_IMPROVING` | 2 improving topics → 2 signals; 0 → none; confidence from occurrenceCount | 4 |
| `RECURRING_WEAKNESS` | totalOccurrences ≥ 3 → signal fires; < 3 → no signal; multiple topics → multiple signals | 4 |
| `RETENTION_RISK` | dueCount > 0, non-RECURRING → signal; dueCount = 0 → none; RECURRING topic with due → captured by RECURRING not RETENTION_RISK | 3 |
| `LEARNING_MOMENTUM` | learningTrend = PROGRESSING → signal; STABLE → no signal; NEEDS_ATTENTION → no signal | 3 |
| `PACE_OBSERVATION` | paceProfile = DECLINING AND sessionCount ≥ 3 → signal; sessionCount < 3 → no signal; paceProfile null → no signal | 3 |
| `STREAK_MILESTONE` | streak = 7 → signal; streak = 5 → no signal; streak = 30 → signal | 3 |
| Sorting | HIGH severity before MEDIUM; MEDIUM before LOW | 2 |
| Signal cap | 6+ conditions met → max 5 returned | 1 |
| Empty profile | new student, 0 data → empty array or only streak signal if active | 2 |
| suppressionKey | each signal has unique key; topic signals include topic in key | 2 |

Target: ~33 assertions.

## 9. Backward Compatibility

### Phase 1

No Phase 1 files are modified. `learningSignals.ts` is a new file. The barrel
export is additive. All 284 Phase 1 test assertions are expected to pass unchanged.

### M2.1 (SM-2 Retention Engine)

Unchanged. `applySM2ForSession` and `errorNotebook.ts` are not touched. The
`dueCount` field on `ActiveWeakness` (which feeds `RETENTION_RISK`) is already
computed by `notebookIntelligence.ts` from `nextReviewAt`.

### M2.2 (Behavior Engine)

`behaviorProfile` is already on `StudentLearningProfile` since M2.2. The signal
engine reads `profile.behaviorProfile` — no additional fetch needed.

### M2.3 (Adaptive Practice)

`difficultyCalibration.ts` and `getPracticeQuestions` are not touched.

### StudentLearningProfile

**Not modified in M2.4.** The profile type gains a `signals` field (or `topSignal`)
in M2.5. In M2.4, signals are only available via `getLearningSignals(userId)` as a
standalone call. This prevents forcing all profile consumers to handle signals before
M2.5 is implemented.

## 10. Risks and Mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| `getStudentLearningProfile` is a heavy call — calling it inside `getLearningSignals` doubles DB load when both are needed | Medium | When M2.5 wires signals into the profile, `getLearningSignals` is retired; callers use profile.signals instead. The double-fetch phase is short-lived. |
| Signal flooding (many conditions met at once) | Low | Hard cap of 5 signals per call, sorted by severity |
| `activeWeaknesses` only contains top 5 topics (capped in Phase 1) | Present | Signals can only fire for topics in the top-5 list. This is acceptable — the top-5 are the most urgent anyway. Noting explicitly so future expansion is deliberate. |
| `behaviorProfile` may be null (OBSERVED tier, all-null) | Low | Each derivation helper null-checks `profile.behaviorProfile` before accessing fields |
| `FIRST_MASTERY` fires on every load once student has exactly 1 mastered topic | Medium | Suppression key `"FIRST_MASTERY"` prevents re-showing within a session window — suppression is caller's responsibility (documented in suppressionKey field) |
